# BR-2609-anvl-001: `anvil_value_get_text` does redundant scanning and has no fast path for escape-free strings

**ID:** BR-2609-anvl-001
**Type:** Bug Report (performance)
**Owner:** anvl
**Filed:** 2026-09-10
**Filed by:** anvil
**Status:** resolved — fix implemented and verified on branch `perf/string-escape-fast-path`
**Branch:** perf/string-escape-fast-path
**Tags:** performance, core, anvil_flat, strings, bindings, flywire

---

## Summary

`anvil_value_get_text` (`src/core/anvil_flat.c`), the accessor every scalar
string read goes through in every binding, does one more full-string scan
than necessary on every call, and has no fast path for strings that contain
no backslash escapes at all — a case that is common in practice (base64
payloads, UUIDs, most identifiers) and is FlyWire's exact real wire shape.
Both are genuine, measured inefficiencies in core Anvil Native, not in any
one binding's marshalling code, so every binding pays the cost equally.

## Found via

FlyWire's real benchmark report,
[`notes/flywire-parse-scaling-benchmark.md`](../notes/flywire-parse-scaling-benchmark.md):
`anvil-node` measured ~1.8x slower per byte than warmed `anvil.js` parsing
FlyWire's real AMP wire format (`AMPacket.pack()`'s output — a short header
plus one large base64-encoded blob string) at production-relevant scale
(n=10,000 records, ~814KB). FlyWire characterized this precisely and asked
the Anvil team to find the mechanism rather than guessing at a fix — this BR
is that answer.

## Root cause 1 — redundant third scan

```c
size_t anvil_value_get_text(anvil_value val, char *buf, size_t buflen) {
   ...
   size_t needed = resolve_string_escapes(v->text.start, (size_t)raw_len, NULL, 0);
   if (buf && buflen > 0) {
      resolve_string_escapes(v->text.start, (size_t)raw_len, buf, buflen - 1);
      size_t term_at = needed < buflen - 1 ? needed : buflen - 1;
      buf[term_at] = '\0';
   }
   return needed;
}
```

`needed` is always computed via a separate `NULL`-buffer sizing scan, even
when a real buffer is already supplied — the second call's own return value
(identical to `needed` by construction, since both scans read the same
source bytes) is discarded. `anvil-node`'s `CopyAnvlText` helper
(`binding.c`) already calls `anvil_value_get_text` twice per conversion
(once to size, once to copy), so one string conversion currently costs three
full passes over the source bytes instead of the achievable two.

## Root cause 2 — no fast path for the zero-escape case

`resolve_string_escapes` (`src/core/anvil_flat.c`, static) is a per-byte
branching loop that checks every byte for a leading `\`, regardless of
whether the string contains any backslash at all. A string with zero
backslashes — true for base64 text, FlyWire's exact payload shape, and
common generally — pays the full per-byte branch cost for no benefit; a
single `memchr` scan for `\` followed by one `memcpy` when none is found is
dramatically cheaper, with the existing per-byte loop kept completely
untouched as the fallback for strings that do contain real escapes.

## Verification

Standalone microbenchmark (`resolve_string_escapes` copied verbatim into a
scratch harness, 813,766-byte base64-alphabet buffer — FlyWire's own
n=10,000 size — 2,000 iterations, `clock_gettime(CLOCK_MONOTONIC)`):

| Fix | Before | After | Savings |
|---|---:|---:|---:|
| Eliminate redundant third scan | 1.0696 ms/call | 0.7232 ms/call | 32.4% |
| `memchr`+`memcpy` fast path (no-escape case) | 0.3627 ms/call | 0.0060 ms/call | 98.3% (~60x) |

The two fixes are independent and compose (both apply to the same call).

## Proposed fix

1. **`anvil_value_get_text`**: when a real, non-NULL buffer is supplied,
   trust `resolve_string_escapes`'s own return value from that call instead
   of a separate sizing pass; only fall back to the `NULL`-buffer sizing
   call for the genuine sizing-only case (`buf == NULL`).
2. **`resolve_string_escapes`**: before the per-byte loop, `memchr` the
   source span for `\`. If none is found, `memcpy` the whole span directly
   and return its length — the per-byte loop only runs when a backslash is
   actually present, and is otherwise byte-for-byte unchanged.

Both changes are behavior-preserving: identical resolved output for every
input, including strings that do contain real escape sequences. Neither
touches N-API/binding code — both land entirely in core Anvil Native
(`src/core/anvil_flat.c`), so the benefit reaches `anvil-node`, `anvil-wasm`,
and any future binding without binding-specific work.

## Implementation

Both fixes landed in `src/core/anvil_flat.c`: `resolve_string_escapes` now
`memchr`s for a backslash up front and takes a `memcpy` fast path when none
is found (existing per-byte loop untouched as the fallback);
`anvil_value_get_text` no longer makes a redundant `NULL`-buffer sizing
scan when a real buffer is supplied — `resolve_string_escapes` already
returns the full resolved length even when `out_cap` truncates what it
writes, so one call now serves both sizing and copying whenever `buf` is
real. New tests `ANV35` (escape-free fast path) and `ANV36`
(truncated-buffer correctness — the returned length must stay the full
resolved length, never the truncated amount actually written) guard both
changes in `test/unit/test_anvil_native.c`. Full regression (unit,
functional against the built `.a`/`.so` in all four debug/release ×
static/shared configurations, and sigma) green; Valgrind reports 0 errors.

## Verification — real before/after numbers

`-O2`, 813,766-byte base64 blob (FlyWire's n=10,000 shape):

- `resolve_string_escapes` alone (isolated function): 0.7158ms → 0.0060ms
  (99.2% faster).
- `anvil_value_get_text` through a real parsed document/value (the
  sizing+copy pattern `anvil-node`'s `CopyAnvlText` uses): 1.0617ms →
  0.0283ms (97.3% faster, ~37x).
- Full pipeline — `anvil_load_buffer` (parse) + statement lookup +
  `anvil_value_get_text`, one call end to end (closest to a real single
  `anvl.parse()`): 4.3458ms → 3.3851ms (22.1% faster). The smaller
  end-to-end number is expected and honestly reported: `anvil_load_buffer`
  itself does one full, unavoidable scan of the document before `get_text`
  ever runs, and that scan is untouched by this fix — at this document
  shape, parsing dominates total time, so eliminating nearly all of
  `get_text`'s cost moves the total by roughly a fifth to a quarter, not by
  orders of magnitude.

These are pure-C, in-process numbers — no N-API boundary crossing, no
V8/JS string handling either side. They don't by themselves establish
where this lands `anvil-node` relative to `anvil.js`; that requires
FlyWire re-running `bench/native-backend-compare.js` against a build with
this fix vendored in. Full writeup, including the methodology mistake
caught and corrected before reporting (an initial before/after comparison
accidentally compared the fixed code against itself, due to a source-copy
ordering bug in the benchmark harness setup — re-run correctly before any
numbers were shared), is in
[`notes/flywire-parse-scaling-benchmark.md`](../notes/flywire-parse-scaling-benchmark.md).

## Resolution

Fixed. Core-level cause understood and eliminated; both changes are
behavior-preserving and land entirely in Anvil Native, benefiting every
binding. Next: bump `anvil-node`/`anvil-wasm`'s vendored `anvil` pin to
this fix and ask FlyWire to re-measure against their real harness, since
the remaining gap (if any) beyond this fix's ~22% end-to-end native-level
improvement likely lives in N-API marshalling or JS-side string handling,
outside this BR's scope.
