# BR-2609-anvl-005: `anvil-wasm` crashes on inputs over ~64KB (stack-allocated string marshaling)

**ID:** BR-2609-anvl-005
**Type:** Bug Report (crash / correctness)
**Owner:** anvl
**Filed:** 2026-09-16
**Filed by:** anvil
**Status:** resolved — fixed and verified on `anvil.wasm` main (`7a6304d`, docs `ba58d48`); no
Core Anvil Native change required
**Tags:** crash, binding, anvil-wasm, emscripten, flywire

---

## Summary

`anvil.parse()`/`parseRawValue()` in `anvil-wasm` reliably failed on real input text once it
crossed roughly 64–73KB — first a silent failure (falsy return, `lastError()` came back
completely empty), then a hard `memory access out of bounds` crash a bit further past that.
Found and reported by FlyWire (`anvil.wasm/notes/flywire-large-input-crash.md`) while extending
their own three-way backend benchmark to finally include `anvil-wasm` at production scale
(10,000-row messages, ~814KB) — every FlyWire message at real scale is well past this threshold,
making it a hard blocker for any real `anvil-wasm` deployment past trivial sizes.

Unlike `BR-2609-anvl-001` through `-004` (a performance investigation), this is a genuine
correctness/crash bug, found via the same ongoing FlyWire collaboration but structurally
unrelated to any of that work.

## Root cause

`lib/index.js` called the two entry points via
`Module.cwrap('anvil_wasm_parse'/'anvil_wasm_parse_raw_value', 'number', ['string'])`. `cwrap`'s
`'string'` *argument* type marshals the JS string onto the **WASM call stack** (Emscripten's
generated `stackAlloc`), not the heap — bounded by `STACK_SIZE`, whose default is 64KB
(65,536 bytes) and which `build.sh` never overrode. Any input text larger than the stack could
actually hold overflowed it, corrupting adjacent memory: a soft, silent corruption just past the
edge (matching the empty-`lastError()` symptom), a harder out-of-bounds trap further past it.

## Verification

**Reproduced independently, not just trusted from the report:** built the existing (unfixed)
`main`, ran a bisection sweep on Linode (real Emscripten toolchain) — parses cleanly through
65,500 bytes, hard crash (`memory access out of bounds`) at 66,000 bytes and every size tested
above that through 100,000 bytes. Matches FlyWire's own bisection almost exactly.

**Confirmed causation, isolating one variable:** built a version with *only*
`-s STACK_SIZE=2097152` (2MB) changed — no code fix at all. The crash disappeared completely
through 2MB inputs. This ruled out any alternative explanation (e.g. a `JsonBuf` growth bug)
before implementing anything.

## Fix

Per FlyWire's own suggested scalable option (not the "just raise the fixed stack size" one):
`cwrap`'s argument type changed from `'string'` to `'number'` (a raw pointer); `lib/index.js`
now marshals the input onto the **heap** itself via a small `withHeapString` helper
(`Module._malloc`/`Module.stringToUTF8`/`Module._free` around the call, freed in a `finally`).
This is bounded only by the heap, which `ALLOW_MEMORY_GROWTH` already lets grow arbitrarily — not
a second fixed ceiling that would just move the same class of problem further out.

**Verified in isolation, not assumed:** built a version with *only* the heap-marshaling fix and
the original, unmodified 64KB stack (no `STACK_SIZE` bump at all) — resolved the crash cleanly
through 5MB inputs on its own. `build.sh` separately bumps `STACK_SIZE` to 1MB as a cheap
defense-in-depth margin for unrelated stack usage (recursion depth from deeply nested documents,
not large scalar values) — confirmed *not* necessary for this specific crash, but reasonable to
keep regardless.

**Verified beyond "doesn't crash":** actual content correctness at scale — byte-exact round-trips
up to 3MB for a single large scalar, and a 5,000-element array, with no truncation or corruption.
Then verified against FlyWire's own real setup directly: their exact repro snippet, and their
real 10,000-row `Table`/`AMPacket` pipeline against real Postgres data (813,766 bytes, their
actual production benchmark shape, synced into a real `flywire` checkout via their own
`scripts/sync-anvil-wasm.js`) — both parse, unpack, and decode correctly end to end.

Two new permanent regression tests (`test/parse.test.js`, `test/parse-raw-value.test.js`) parse
real content at 65,500 / 200,000 / 1,000,000 bytes and assert byte-exact round-trip content, not
just "didn't throw" — full existing suite (37 tests, up from 35) passes.

## Resolution

Fixed, verified in isolation and against FlyWire's real production shape, merged to `anvil-wasm`
main, and documented back to FlyWire in the same notes file they filed the report in. The silent-
failure symptom (empty `lastError()` just below the crash threshold) needed no separate fix — it
was a downstream consequence of the same stack corruption, and no longer occurs once the root
cause is fixed. No Core Anvil Native change was needed; this was entirely a binding-layer
(Emscripten glue) issue, same pattern as `BR-2609-anvl-004`.
