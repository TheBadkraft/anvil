## Summary

`source_from_buffer` (`src/core/source.c`) computes an FNV-1a 64-bit content hash over the
*entire* document buffer, unconditionally, on every single load — including the root document
of a one-off `anvil_load_buffer` call, and including AMP documents, which structurally can never
participate in an import graph at all (AMP forbids `import` outright). This byte-by-byte hash
(one 64-bit multiply per byte) is a genuine, measured bottleneck: on FlyWire's real 813,766-byte
`@bin`-blob AMP message, it accounts for **~98% of `anvil_load_buffer`'s entire remaining cost**
after `BR-2609-anvl-002`'s parser fix.

## How this was found

Using the parser's own existing instrumentation (`anvl_parser_set_hook`,
`include/internal/parser.h` — not an ad hoc timer) confirmed `BR-2609-anvl-002`'s fix is working
exactly as intended: pure body-parsing (`parse_source`) on the largest test document costs only
~0.015 ns/byte, essentially free. But `anvil_load_buffer` as a whole still cost ~0.87 ns/byte —
meaning something *other* than parsing accounted for the difference. Splitting `load_common`'s
phases (`doc_load_source`+register / `scan_header` / `load_imports` / `create_arena` /
`parse_body` / `resolve_context`) with direct per-phase timing showed `doc_load_source` alone —
not parsing — was ~98% of the total. Isolating `source_from_buffer`'s own `memcpy` vs. its
`source_compute_hash` call confirmed the hash, not the copy, was the cost: `memcpy` measured
0.014 ns/byte; the FNV-1a hash measured 0.849 ns/byte — a ~60x difference.

## Root cause

```c
static uint64_t source_compute_hash(const char *data, usize len) {
   uint64_t hash = FNV1A_OFFSET;
   for (usize i = 0; i < len; i++) {
      hash ^= (uint8_t)data[i];
      hash *= FNV1A_PRIME;
   }
   return hash;
}
```

A textbook byte-wise FNV-1a: one 64-bit multiply per byte, each one sequentially dependent on
the previous (the multiply-dependency chain is exactly as long as the input). Called
unconditionally from `source_from_buffer` (`src/core/source.c`) for every document load, file or
buffer, root or import.

**Why this is real, unavoidable-looking work that's actually often wasted:** the hash feeds
`mod_ctx_register_doc`'s registry key (`Registry.add`/`Registry.find`, keyed by
`Source.hash(doc->source)`) and diamond-import deduplication (`mod_load_imports`, detecting the
same file content reached via two import paths — `src/core/module.c`). Both are real, correct
uses. But the root document being loaded directly is never itself an import target within its
own load, and an AMP document can never appear in an import graph at all (AMP forbids `import`
outright) — so for FlyWire's exact workload (one AMP message per `anvl.parse()` call), this cost
is paid on every single call for a capability that document can never use.

## Fix — considered and rejected: skip/defer the hash

Changing *when or whether* hashing happens would touch a correctness-critical path
(`mod_ctx_register_doc` requires a non-zero hash to register at all; the registry is described as
process-wide, so even the root's own hash participates in duplicate-registration detection, not
just import dedup). Rather than risk that invariant, the fix is a straight algorithmic swap with
zero semantic change: process 8 bytes per multiply instead of 1, cutting the sequential
multiply-dependency chain length by 8x.

```c
static uint64_t source_compute_hash(const char *data, usize len) {
   uint64_t hash = FNV1A_OFFSET;
   usize i = 0;
   for (; i + sizeof(uint64_t) <= len; i += sizeof(uint64_t)) {
      uint64_t word;
      memcpy(&word, data + i, sizeof(word));
      hash ^= word;
      hash *= FNV1A_PRIME;
   }
   for (; i < len; i++) {
      hash ^= (uint8_t)data[i];
      hash *= FNV1A_PRIME;
   }
   return hash;
}
```

No caller depends on a *specific* hash value — confirmed by grepping every test and call site
(`test/unit/test_source.c`, `test_document.c`, `test_registry.c`, `test_header.c`,
`test_module.c`): every one checks determinism, non-zero-ness, or content-sensitivity
(same content → same hash, different content → different hash), never a literal number. Those
properties are fully preserved.

## Verification

Isolated (813,766-byte base64-alphabet buffer, 500 iterations):

| | before (byte-wise) | after (word-wise) | change |
|---|---:|---:|---:|
| hash alone | 0.851 ns/byte | 0.104 ns/byte | 87.8% faster (~8.2x) |

Real document, real `@bin` shape:

| | before (post-BR-002) | after | change |
|---|---:|---:|---:|
| `anvil_load_buffer` alone | 0.7109ms | 0.1198ms | 83.1% faster (~5.9x) |
| full pipeline (parse+lookup+get_text) | 0.7620ms | 0.1655ms | 78.3% faster (~4.6x) |

Combined with `BR-2609-anvl-002`, full pipeline vs. the original pre-BR-2609 baseline: 2.4150ms →
0.1655ms — **93.1% faster overall, ~14.6x**.

New tests `SRC47`–`SRC49` (`test/unit/test_source.c`) cover word-boundary correctness: a
difference inside a full 8-byte word, a difference only in the tail (content not a multiple of
8 bytes), and hash stability at lengths straddling the word boundary (7/8/9 bytes). Full
regression green (unit, functional across all four debug/release × static/shared configurations,
sigma), Valgrind-clean.

## Real-world verification — the crossover is gone

Vendored pins bumped in both bindings (29/29 `anvil-node`, 30/30 `anvil-wasm`), rebuilt. Ran
FlyWire's own expanded `bench/native-backend-compare.js` (fresh process per scale, both
single-call and warmed conditions) against real Postgres BULKGEN data:

**True single-call, fresh process, by scale:**

| n | bytes | anvil-js | anvil-node | speedup |
|---:|---:|---:|---:|---:|
| 100 | 8,564 | 1.230ms | 0.098ms | 12.5x |
| 1,000 | 81,765 | 3.503ms | 0.236ms | 14.9x |
| 2,000 | 163,102 | 3.737ms | 0.365ms | 10.2x |
| 3,000 | 244,434 | 4.185ms | 0.417ms | 10.0x |
| 5,000 | 407,102 | 4.015ms | 0.604ms | 6.6x |
| 7,000 | 569,766 | 4.638ms | 0.793ms | 5.9x |
| 10,000 | 813,766 | 5.125ms | 1.227ms | **4.2x** |

**Warmed:**

| n | anvil-js | anvil-node | speedup |
|---:|---:|---:|---:|
| 100 | 0.437ms | 0.023ms | 19.3x |
| 1,000 | 0.658ms | 0.043ms | 15.3x |
| 10,000 | 1.730ms | 1.100ms | **1.6x** |

There is no longer a crossover at any tested scale, in either condition. Before this fix (still
on `BR-2609-anvl-002` alone), `anvil-node` fell to ~1.1x *slower* than `anvil-js` at n=10,000
single-call; it is now consistently faster everywhere, from 100 to 10,000 records.

## Resolution

Fixed, verified against both the isolated microbenchmark and FlyWire's real harness, merged, and
vendored into both bindings. This closes the investigation started by FlyWire's original
benchmark report (`notes/flywire-parse-scaling-benchmark.md`) and continued through
`BR-2609-anvl-001` and `BR-2609-anvl-002` — three real, independent inefficiencies found and
fixed in core Anvil Native (redundant string-escape scanning, byte-by-byte blob-content scanning,
byte-wise content hashing), none of them binding-specific, all benefiting every binding equally.
