## Summary

`parse_blob_literal` (`src/core/parser.c`) scans a blob's content span one byte at a time via
`Source.consume(src, 1)`/`Source.peek(src)` — a vtable-indirect function call per byte — instead
of a single bulk scan for the closing delimiter. For a large blob (FlyWire's real AMP wire
shape wraps its entire binary payload as one `@bin\`<base64>\`` blob, routinely hundreds of
kilobytes), this dominates the parser's own cost: isolating `anvil_load_buffer` alone on an
813,766-byte `@bin` blob costs **2.37ms**, of which the byte-by-byte scan loop alone accounts for
roughly **1.1ms** (measured in isolation, matching the real-world share). This is a genuine,
long-standing inefficiency in core Anvil Native, not binding-specific — every binding pays it.

## How this was found — BR-2609-anvl-001 fixed something real, just not this

BR-2609-anvl-001 fixed two real inefficiencies in `anvil_value_get_text`/
`resolve_string_escapes`, verified against FlyWire's benchmark
(`notes/flywire-parse-scaling-benchmark.md`). Real end-to-end re-testing against FlyWire's own
harness (`bench/native-backend-compare.js`) afterward showed only a ~6% improvement, far short of
the ~22% the pure-C estimate predicted — prompting a deeper investigation into the N-API
marshalling layer as the suspected remaining cost.

That investigation found something more fundamental first: **FlyWire's real payload field is a
`@bin`-tagged BLOB (`payload := @bin\`<base64>\`;`, `src/am-packet.js`), not a quoted STRING** as
BR-2609-anvl-001's benchmark had assumed from an imprecise English description in FlyWire's
original report ("one `blob := "<base64>"`-shaped value"). A BLOB's `anvil_value_get_text` never
calls `resolve_string_escapes` at all — it takes the direct `copy_to_buffer` raw-span path, which
was already fast before BR-2609-anvl-001. Confirmed directly: `get_text` on the real `@bin` shape
costs a negligible 0.013ms both before and after that fix. **BR-2609-anvl-001's fix is real and
correct, but it was never on FlyWire's actual hot path** — isolating `anvil_load_buffer` alone
(no `get_text` call at all) on the same document showed it accounts for essentially the entire
2.37ms per-call cost. The bottleneck was always in parsing, not in reading the parsed value back
out — this BR is the corrected diagnosis and its fix.

## Root cause

```c
// Parse the blob content until the closing brace or EOF
while (!Source.is_eof(src) && Source.peek(src) != ANVL_TOK_BACKTICK) {
   Source.consume(src, 1); // Consume blob content character
}
```

Three vtable-indirect calls per byte of blob content (`is_eof`, `peek`, `consume`), each with its
own internal bounds-checking and (for `consume`) line/column bookkeeping — for an 810KB blob,
roughly 2.4 million indirect calls to scan content that a single `memchr` pass could cover in one
shot. `parse_string_literal` has the identical byte-by-byte pattern (escape handling makes its
fast path more subtle — out of scope for this BR, flagged as a related follow-up).

## Verification

Isolated the exact loop pattern (mirroring the real vtable-indirect call structure) against an
813,766-byte buffer, 300 iterations:

| | before (byte-by-byte) | after (memchr + bulk line/col update) | change |
|---|---:|---:|---:|
| scan loop alone | 1.0962ms | 0.0058ms | 99.5% faster (~189x) |

Real document, real `@bin` shape, full pipeline (`anvil_load_buffer` + statement lookup +
`get_text` x2):

| | before | after | change |
|---|---:|---:|---:|
| `anvil_load_buffer` alone | 2.3691ms | 0.7067ms | 70.2% faster (~3.4x) |
| full pipeline | 2.4150ms | 0.7620ms | 68.4% faster (~3.2x) |

## Fix

Added `Source.consume_until(src, delim)` (`include/internal/source.h`, `src/core/source.c`) — a
bulk equivalent of `while (!is_eof(src) && peek(src) != delim) consume(src, 1);`: one `memchr`
scan for the delimiter, then one pass over just the skipped span counting embedded newlines (for
line/col bookkeeping identical to the byte-by-byte loop it replaces — the one correctness
property that could not be traded away for speed, since later error messages depend on accurate
positions). `parse_blob_literal` now calls it directly in place of the loop. Six new tests
(`SRC42`–`SRC46`) cover delimiter-found, delimiter-never-found (EOF), embedded-newline
line/col correctness, NULL safety, and the zero-length-skip edge case.

**A second, unrelated bug found and fixed in the process:** the root `Makefile`'s incremental
object-file build (`build/{debug,release}/*.o`) had no header dependency tracking — a `%.o: %.c`
rule with no header prerequisites. Adding `consume_until` to `anvl_source_i` (a struct field
insertion, changing every later field's offset) exposed this: some already-built objects that
`#include "internal/source.h"` were not recompiled, producing a library archive with inconsistent
vtable layouts between translation units — silent corruption, no build error, only visible as
`test/functional`'s suite (which links the *built* library artifact, not source) failing on
completely unrelated basic parses. Fixed by adding `-MMD -MP` to both `DEBUG_CFLAGS` and
`RELEASE_CFLAGS` and including the generated `.d` files, so a header-only change now correctly
triggers every dependent object's rebuild. Verified directly: touching only the header (no `.c`
edit) now rebuilds `anvil_flat.c`/`document.c`/`module.c`/`parser.c`/`resolver.c`/`source.c`/
`source_registry.c` as expected. `test/unit` was unaffected throughout (each test binary compiles
all sources fresh in one invocation, no incremental object cache), which is why this was only
visible through `test/functional`.

## Resolution

Fixed, verified (full unit/functional/sigma regression green across all four
debug/release × static/shared functional configurations, Valgrind-clean), and merged. Both the
parsing fix and the Makefile dependency-tracking fix are real, independent improvements — the
former closes a genuine performance gap on FlyWire's actual workload shape; the latter closes a
class of silent-corruption risk for any future header change to this repo's public/internal
interfaces. `parse_string_literal`'s identical byte-by-byte pattern is a related, not yet
addressed opportunity — noted for a future pass, out of scope here since string escape handling
makes a naive `memchr` fast path insufficient on its own. Next: bump `anvil-node`/`anvil-wasm`'s
vendored pins to this fix and re-run FlyWire's real harness (`bench/native-backend-compare.js`)
— this is the fix that should actually move the measurement BR-2609-anvl-001's didn't.
