# BR-2609-anvl-004: N-API/JS-boundary call volume dominates binding conversion cost for many-small-value documents

**ID:** BR-2609-anvl-004
**Type:** Bug Report (performance)
**Owner:** anvl
**Filed:** 2026-09-13
**Filed by:** anvil
**Status:** resolved — fixed in `anvil-node` (main `9646acc`) and `anvil.wasm` (main `7b78aa8`); no
Core Anvil Native change required
**Continues:** [`BR-2609-anvl-003`](BR-2609-anvl-003.md) — that fix (word-wise content hash)
closed the investigation into FlyWire's `@bin`-blob wire shape. This BR is a distinct, later
finding: a different FlyWire wire shape (`@table`, an array of tuples) surfaced a real cost in
each binding's *own* value-conversion layer, not in core Anvil Native at all.
**Tags:** performance, binding, anvil-node, anvil-wasm, N-API, flywire

---

## Summary

FlyWire reported 19–27ms to parse 10,000 records via the `@table` payload format (`Table.decode()`
in `src/table.js`, calling `anvl.parseRawValue()` on an ANVL array-of-tuples text — 10,000 rows ×
10 fields = 100,000 leaf scalar values, per the real `assets.meta.anvl` schema). Asked directly
to check `parseRawValue()` for the same class of redundant-scanning bug as `BR-2609-anvl-001`
through `-003` — none was found there. The real cost was one level up: each binding's *own*
conversion of an already-parsed `anvil_value` tree into a JS value.

## Root cause — two different bindings, two different problems

**`anvil-node`:** `AnvilValueToJs`/`AnvilCollectionToJs`/`AnvilObjectToJs` built one real
`napi_value` per leaf value — one `napi_create_string_utf8`/`napi_create_double`/
`napi_set_element` N-API call per field, at volume. Isolated directly: building the *exact same
shape* (10,000 arrays of 10 elements each, no Anvil Native or malloc involved at all) using only
raw N-API calls cost **~7–10ms by itself** — comparable to or exceeding the actual parse cost.

**`anvil.wasm`:** already used a smarter strategy (build one JSON string in C, one boundary
crossing, let V8's native `JSON.parse()` materialize the tree) — but its own shipped
`jsonbuf_append_json_string` and numeric-conversion code had two independent, real
inefficiencies of their own, found while porting this same strategy to `anvil-node`:
1. The escaping loop called one function (with a capacity check) *per character*, even when
   nothing needed escaping — the same class of bug as `BR-2609-anvl-002`, in the binding layer
   instead of core Anvil Native.
2. Numeric conversion always round-tripped through `strtod`+`snprintf("%.17g", ...)`
   (~106ns/call, measured) even though ANVL's numeric grammar is a strict subset of JSON's (the
   one exception — a leading zero — needs a cheap check and rare fallback); the common case can
   copy the raw source text through directly.

**Core Anvil Native itself needed no change.** `anvil_parse_value_fragment`'s own cost on this
exact shape was verified separately, via the parser's own `anvl_parser_set_hook` instrumentation:
genuinely linear, ~9.86ms at n=10,000 — the parser was never the bottleneck here.

## Fix

`anvil-node`: ported `anvil.wasm`'s `JsonBuf`/`append_anvil_value_json*` approach (build one JSON
string in C, one `napi_create_string_utf8` call for the whole result, `JSON.parse()` on the JS
side) — with both of `anvil.wasm`'s bugs fixed from the start in the ported code, not carried
forward. `Parse()`/`ParseRawValue()` rewritten in `src/binding.c`; `lib/index.js` updated to
`JSON.parse()` the returned string. JS-visible contract unchanged (same return shapes, same
null-vs-genuine-ANVL-null disambiguation via `lastError()`).

`anvil.wasm`: the same two bug fixes (bulk-scan escaping fast path, numeric raw-copy fast path)
applied directly to its own already-shipped `jsonbuf_append_json_string`/
`append_anvil_value_json`.

Both fixes are behavior-preserving — confirmed by full existing test suites passing unmodified in
each repo, plus new tests covering the previously-unexercised code paths directly (leading-zero
numeric fallback, escape correctness at run boundaries, buffer growth beyond initial capacity,
the real FlyWire Table shape end to end).

## Verification

Isolated (813KB-scale buffers, matching prior BR methodology):

| | before | after |
|---|---:|---:|
| Pure N-API tree build (`anvil-node`, no Anvil Native/malloc) | ~7–10ms | *(eliminated — replaced by JSON-string strategy)* |
| JSON-string build alone, naive port | 7.55ms | — |
| JSON-string build, escaping fast path only | 6.41ms | — |
| JSON-string build, both fast paths | — | 3.35ms |

Real, real-harness verification (`anvil-node`, FlyWire's actual `Table.decode()`, n=10,000, five
consecutive runs against the actual built module — not the isolated prototype):

| | before | after | change |
|---|---:|---:|---:|
| `Table.decode()` total | 27.057ms | ~22.2ms | **~18% faster** |

An earlier reported figure (34.3%) was based on an inconsistent comparison — an isolated
prototype measuring "native conversion + `JSON.parse()`" only, compared against a baseline that
also included `Table.decode()`'s own JS-side row-remapping loop (present, and equally costly, in
both the old and new implementation). Caught and corrected before being treated as final; the
18% figure above is the honest, apples-to-apples number, measured against the real built module
through FlyWire's own code.

`anvil.wasm`: full test suite (35 tests, including 5 new ones covering the two fixes directly)
passes, built and verified on the real Emscripten toolchain (Linode).

## Resolution

Fixed in both bindings that needed it. `anvil-wasm`'s existing JSON-boundary architecture was
already the right shape — it needed two targeted bug fixes, not a rewrite. `anvil-node` needed
the larger change (adopting that same architecture) since it was building N-API values directly.
`anvil.net` is unaffected — it doesn't wrap Anvil Native today (confirmed: no `DllImport`/P-Invoke
into it anywhere), so this class of binding-conversion cost doesn't apply there yet. No further
action needed unless a future many-small-values workload surfaces a cost inside the JSON-string
build step itself (currently ~3.35ms at this scale, not investigated further since it wasn't the
dominant remaining cost).
