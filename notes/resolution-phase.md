# Resolution Phase (phase 4)

**Status: implemented and GREEN.** `mod_resolve_context` (`src/core/resolver.c`) builds `ctx->identifiers`, validates every `base`, and resolves every `$identifier` VarRef — see "Implementation" below for the summary, or the design sections that follow for the full reasoning. This note collects resolver design reasoning that had accumulated inside `document-body-parse.md` while body-parse was being designed — moved out because Resolution is its own iteration, not part of body-parse. `document-body-parse.md` keeps only short boundary statements ("this is the resolver's concern") with pointers back here.

## Context

Resolution is the fourth and final phase of the document pipeline:

```
1. Header scan     — doc_scan_header
2. Import loading  — mod_load_imports
3. Body parse      — doc_parse_body
4. Resolution      — this note
```

It runs once, post-parse - after every document in the import graph has been body-parsed — not per-document, and not in any particular order (see "Why document processing order doesn't matter" below).

## Design sketch: a global identifier map, not order-dependent traversal

`derived : base { ... };` resolves by looking `base` up in a map that's already complete by the time any resolution happens, because Resolution is a _post-parse process_, after every document in the import graph has been body-parsed. As long as that phase boundary holds — all bodies parsed before any resolving begins — order among documents doesn't matter; the resolver only fails when a lookup misses, never because of processing order.

**Confirmed shape for the map itself** (settled while designing VarRef resolution, below — this piece is no longer a sketch): one `map identifiers` (Sigma's `sigma/map.h` — byte-string-keyed, FNV-1a, no hand-rolled hashing needed) lives on `module_context`, alongside `ctx->values`/`ctx->statements`, built once by `mod_resolve_context` before any lookups happen. Built by walking every `module_document` in `ctx->docs` and, for each, only its **top-level** statements (`doc->body` — not the flat `ctx->statements` index, which also includes nested statements and would wrongly make them resolvable targets): `Map.set(identifiers, stmt->name.start, slice_len(stmt->name), (addr)stmt)`. Living on the context, not built privately inside whichever resolution mechanism needs it first, is deliberate — `base`/inheritance resolution needs the exact same top-level-name lookup and should reuse this same map rather than building its own.

**Duplicate names are a hard error, full stop** — any duplicate top-level name fails resolution immediately, whether the collision is between two statements in the same document or across an import boundary (matches `aml-import-namespace-rules.md` §2's "collisions across imported documents fail fast," extended uniformly since the map itself has no way to distinguish origin once flattened, and a duplicate name is equally ambiguous for lookup purposes either way). Implemented as `ANVL_ERR_RESOLVER_DUPLICATE_IDENTIFIER` (4053, `include/errors.h`) — a new code, added alongside the three already sitting pre-reserved in the same "Resolver Errors (405x)" block (see "Implementation" below).

The legacy (`anvil.bak`) `anvl_resolver_build_state` was reviewed for precedent: its hand-rolled FNV-1a `anvl_id_map_t` (raw byte-offset/length keys) is exactly this "global identifier map" idea, already proven — but Sigma's `Map` supersedes the hand-rolled table entirely (same hashing scheme, already implemented, already tested). Its Kahn's-topological-sort cycle detection, however, does **not** carry over as a *mechanism* — that validates an entire inheritance graph upfront via adjacency lists and a queue, which is more machinery than this project's `base` relation needs (see "Field-merging inheritance" below for why the same hop-counter trick as VarRef resolution covers it instead). Its *policy* does carry over, though: a `base` cycle is confirmed as a hard error (`ANVL_ERR_RESOLVER_CYCLE_DETECTED`), unlike VarRef chains, which resolve missing/cyclic references to `null` rather than erroring (see "VarRef resolution" below) — a cyclic inheritance chain can't produce a sensible merged object at all, where a null VarRef is a perfectly normal outcome.

## VarRef resolution

Consumes `ANVL_VALUE_VARREF` values produced by body-parse (see `document-body-parse.md`'s "`$` VarRef reinstated" note) and the `identifiers` map above. Two steps, both in `mod_resolve_context`, map-build first:

1. **Find every VarRef in one flat pass.** `ctx->values` already indexes every `anvl_value` allocated anywhere in the context, at any nesting depth (array/tuple element, object field, however deep) — the same flat index `mod_ctx_dispose` uses to release `.collection.items`/`.object.statements` without recursing the tree. Filtering that one pass for `type == ANVL_VALUE_VARREF` finds every reference in the whole context; no separate tree walk needed.
2. **Resolve each one, chasing chains to the end.** Look `v->varref.target` up in `identifiers`. If the target statement's own value is itself a `VARREF`, keep following it — `a := $b; b := $c;` resolves `a` all the way to `c`'s concrete value, not just one hop to `b`. Whether the chase ends in a miss or a cycle, the result is the same: no error, just an unresolved reference (see `document-body-parse.md`'s established policy — "an unmatched reference and a genuine cycle are treated the same way, deliberately"). A target that names an *anonymous* (`OBJECT_BLOCK`) statement is treated the same way too — resolves to unresolved, not an error — since that decision was made (open question #1, below): an `OBJECT_BLOCK` statement has no `anvl_value` of its own to alias at all (only `->body`, never `->value`), so there's nothing a VarRef could even point to.

   **Cycle detection needed no visited-set, in the end** — a hop counter is enough. With `N` distinct names in `identifiers`, any non-cyclic chase consumes at most `N` distinct names before terminating (a hit or a miss); still going after `N + 1` hops means some name was necessarily revisited. `resolve_varref_chain` (`src/core/resolver.c`) just caps its loop at `Map.count(ctx->identifiers) + 1` and declares a cycle if it falls through — no allocation, no set to maintain.

**Storage: `v->varref.resolved` is a plain pointer to the target's own `anvl_value` node** — a new field on the `varref` union member, aliasing it directly rather than copying it. This was the natural instinct going in ("just reference the referenced identifier's value") but needed checking against the usual worry with raw pointers — dangling references if the pointee could be freed early. That worry doesn't apply here: every `anvl_value`/`anvl_statement` in a `module_context` lives in one shared arena, disposed as a single block by `mod_ctx_dispose` — no node is ever freed independently of every other node in the same context. A pointer between two nodes in that arena is exactly as safe as a duplicated slice or a duplicated struct, without their downsides (a text-only slice loses type/union information entirely and can't represent an ARRAY/TUPLE/OBJECT target at all; a full struct copy duplicates a `list` handle that must then never be independently disposed, for no actual benefit). `resolved` defaults to `NULL` (unresolved: never chased, missing target, cycle, or anonymous target) — a resolved VarRef's `type` stays `VARREF` and `.text`/`.varref.target` stay intact for diagnostics; `.varref.resolved` is purely additive. Declared as `struct anvl_value_t *resolved;` rather than the `anvl_value` alias — the alias typedef isn't visible yet at the point this field is declared, inside `anvl_value_t`'s own definition (a self-reference has to spell out the struct tag).

## Field-merging inheritance

Consumes `stmt->base` (validated by `validate_bases` above) and `identifiers`. Actually copies/overrides a derived statement's effective field set from its base's — the piece explicitly left undesigned when `validate_bases` first landed (that only checked whether `base` was a *legal* target, never merged anything).

**Storage: mutate the derived statement's own field list in place — no separate merged view.** This was a deliberate call, and a correction to an earlier instinct: a non-destructive "here's the merged view, but the original own-fields list is still there too" design (mirroring `.varref.resolved`'s non-destructive aliasing) was floated first, but rejected — with two lists potentially describing the same object's fields (one own-only, one merged), there's a real risk of a shadow/duplicate representation drifting inconsistent, or a consumer reading the wrong one. Mutating in place avoids that entirely: after `merge_all_inheritance` runs, `stmt->body` (`OBJECT_BLOCK`) or `stmt->value->object.statements` (`ASSIGN` with an object value) *is* the complete, correct field set — there is only ever one list to read. What actually gets appended is still non-destructive at the *node* level, matching `.varref.resolved`'s own reasoning: an inherited field is an **aliased** `anvl_statement` pointer from the ancestor's own list, never a copy — the same node is referenced from both the ancestor's list and the derived's list, safe for the same reason a VarRef's pointer-aliasing is safe (one shared arena, one disposal pass, no per-node ownership to conflict over).

**No recursion, no memoization, no per-statement cache field — the same hop-counter trick as VarRef resolution covers this too.** `base` is a single slice per statement, so the "inherits from" relation never branches — exactly the same functional-graph shape VarRef's `target` chase already exploited. `merge_inherited_fields` (`src/core/resolver.c`) walks the base chain nearest-ancestor-first, capping at `Map.count(identifiers) + 1` hops; for each ancestor, it appends any of *that ancestor's own* fields not already present by name in the derived statement's (growing) field list, then continues to that ancestor's own base, and so on to the root. Two things fall out of this for free, without being designed in separately:
- **Override precedence.** Since nearer ancestors are processed first and an already-present name is always skipped, a closer override — derived's own field, or an intermediate ancestor's — always beats a farther one.
- **Transitivity.** `c : b : a` doesn't need `b` to have already been merged with `a` before `c` is processed — `c`'s own walk continues past `b` to `a` regardless, re-checking names it may have already picked up via `b`'s (possibly still-unmerged) own list. This makes the whole pass **order-independent**: `merge_all_inheritance` can process every statement with a `base` in any order (it walks `ctx->statements` in flat-index order, but nothing about correctness depends on that) and still reach the same final result. The only cost is occasionally re-walking a shared ancestor's fields more than once across different derived statements — harmless (a name already present is just skipped) and not worth optimizing away at Anvil's document scale.

A cycle (`a : b := { ... }; b : a := { ... };`) is only reachable here at all because `validate_bases` already rejected any cycle involving an anonymous (`OBJECT_BLOCK`) link — both statements in a real cycle must be legal, `ASSIGN`-with-object-value base targets. When the hop cap is exceeded, `merge_inherited_fields` reports `ANVL_ERR_RESOLVER_CYCLE_DETECTED` (4050) — the one Resolver-Errors code that had sat reserved and unused until this piece landed.

## Why document processing order doesn't matter

Body-parse only reads its own document's source (see `document-body-parse.md` § *Responsibilities of the body parse*). Under the global-identifier-map design above, this makes `aml-import-namespace-rules.md` § 7's "parse bodies in reverse dependency order" requirement unnecessary under this design, not just unproven — the map is complete before any resolving starts, so no document needs another document's body to already be parsed.

`notes/document-header-scan.md` § *Deferred to Resolution phase* separately corrects `aml-import-namespace-rules.md` § *Import graph order*'s claim that reversing DFS discovery (pre-order) gives a valid bottom-up order — that reasoning is still wrong under diamond imports (this project explicitly supports them, `HDR13`) regardless of whether anything ends up needing the order fixed.

## Open questions

1. ~~"Cannot be inherited but can be derived": whether something is a legal target to inherit/derive from is entirely the resolver's concern — `doc_parse_body` just captures `base` syntactically and never judges it. The distinction itself is still not understood.~~ **Resolved.** "Anonymous object" names the `OBJECT_BLOCK` statement form specifically — `foo { statements };` (`ANVL_STMT_OBJECT_BLOCK`, no `:=`) — already called "anonymous blocks" once in passing in `document-body-parse.md`'s Resolved Questions #2, which this note failed to connect at the time. It's "anonymous" not because it lacks a name (it doesn't — `foo` is right there) but because the object body has no life of its own independent of that one statement: immutable, not overridable. `foo := { statements };` (`ANVL_STMT_ASSIGN` with an `ANVL_VALUE_OBJECT` value) is the "classical" counterpart, and the only one of the two that's a legal `base` target.
   - **The rule**: resolving a `base` reference means looking the target statement up in `identifiers` and rejecting it if `target->kind == ANVL_STMT_OBJECT_BLOCK` — an anonymous object can never be inherited from. **Hard error, full stop** (confirmed — same severity as a duplicate name, not a silent no-fields-to-merge fallback). Implemented using `ANVL_ERR_CANNOT_INHERIT_FROM_ANONYMOUS` (4052) — found already sitting pre-reserved in `include/errors.h`'s "Resolver Errors (405x)" block (alongside `ANVL_ERR_RESOLVER_CYCLE_DETECTED`/`ANVL_ERR_RESOLVER_MISSING_BASE`) once implementation actually started, with a message ("Cannot inherit from anonymous object (use ':=' for inheritable declarations)") that independently confirms this exact reading of "anonymous" — no invented code needed after all.
   - **"But a derived child can be anonymous"**: an anonymous (`OBJECT_BLOCK`) statement can still itself carry `: base`, deriving from something else — it just can never *be* someone else's base in turn. No grammar gap here: both statement forms already accept `[: base]` in the same position (`document-body-parse.md`'s Resolved Questions #2 — `derived : base { ... };` and `derived : base := { ... };` are equally valid today), so this is purely the resolver-side check above, nothing for `doc_parse_body`/`parse_statement` to change.
2. ~~Static value reference mechanism: `derived_var := base_var;` (`ANVL_VALUE_IDENTIFIER`) resolves once at Resolution time via the global identifier map above. The resolver mechanism itself — construction, lookup, error reporting on a miss — is not yet designed.~~ **Resolved — see "VarRef resolution" above.** Superseded on two fronts: the reference syntax itself moved from a bare identifier (`ANVL_VALUE_IDENTIFIER`) to the reinstated `$identifier` sigil (`ANVL_VALUE_VARREF`, implemented in `src/core/parser.c`), and the resolution mechanism — map shape, chain-following, storage on the value node — now has a confirmed design, not just a lead.
3. **Resolver-vs-body-parse boundary, for reference**: `doc_parse_body` captures `base` as a slice and nothing more; it doesn't care what it points to or whether inheriting from it is allowed. That boundary is settled (see `document-body-parse.md` § *Resolved questions*) — what's open here is everything on the resolver's side of it.

## Implementation

`mod_resolve_context(module_context, anvl_err_code *)` (`include/internal/module.h` prototype, `src/core/resolver.c` implementation) runs four pieces in sequence — `identifiers` build (with duplicate detection), `base` validation, field-merging inheritance, then VarRef resolution — stopping at the first hard error.

- `include/internal/module.h`: `ctx->identifiers` (a `map`) added to `struct anvl_mod_ctx_t`; `.varref.resolved` added to `anvl_value_t`'s `varref` union member; `mod_resolve_context` prototyped.
- `include/errors.h` / `src/core/errors.c`: `ANVL_ERR_RESOLVER_DUPLICATE_IDENTIFIER = 4053` added (message + name table entries) alongside the three already-reserved Resolver Errors codes; all four now in active use (`ANVL_ERR_RESOLVER_CYCLE_DETECTED` by field-merging, `ANVL_ERR_RESOLVER_MISSING_BASE`/`ANVL_ERR_CANNOT_INHERIT_FROM_ANONYMOUS` by `base` validation, `ANVL_ERR_RESOLVER_DUPLICATE_IDENTIFIER` by the `identifiers` build).
- `src/core/module.c`: `mod_ctx_dispose` releases `ctx->identifiers` (`Map.dispose` — keys and values are both arena-owned, borrowed, nothing to free but the map's own bucket storage, same non-owning relationship `ctx->statements`/`ctx->values` already have to the arena).
- `src/core/resolver.c` (new file): `build_identifiers`, `validate_bases`, `own_fields`/`fields_has_name`/`merge_inherited_fields`/`merge_all_inheritance`, `resolve_varref_chain`/`resolve_varrefs`, and `mod_resolve_context` itself.
- `test/unit/test_resolver.c` (14 cases `RSV01`–`RSV14`, 73 assertions): duplicate name (same document, and across a merged import via a new `resolver_dup_import.anvl` fixture), VarRef single-hop/chain/cycle/missing-target/anonymous-target, `base` missing/anonymous/valid, and field-merging (append+override, transitive three-level chain, `OBJECT_BLOCK`-form derived, inheritance cycle rejected). All passing, Valgrind-clean.
- Wired into both `test/unit/Makefile` and `test/infra/Makefile`'s `ANVIL_SRCS`/`all`/per-binary targets, matching every other `src/core/*.c` file's build integration.
- Full regression (source, module, header, document, registry, body_amp, body_aml, resolver) green; resolver re-confirmed Valgrind-clean after field-merging landed.
