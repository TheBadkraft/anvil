## Future feature ideas (not scheduled to any phase)

- **Import a dynamically-built, file-less source (in-memory "virtual" import target)**: today `import_load_child` (`src/core/module.c`) only ever resolves an import via `doc_load_source(..., ANVL_SOURCE_FROM_FILE, ...)` — there's no way for a document built at runtime via `Source.from_buffer` (no real file behind it) to be the target of another document's `import "...";`. Raised as a design exercise: a dev builds an ANVL source on the fly (e.g. shared base-object definitions), and wants a second, separately-authored stream source to `import` it, with no OOP builder-class API to lean on (that doesn't exist yet).
  - What already works with zero code changes: `doc_load_source(doc, ANVL_SOURCE_FROM_BUFFER, ...)` loads the in-memory source, and `mod_ctx_register_doc(ctx, doc, filepath, ...)` accepts *any* string as `filepath` — nothing requires it to be a real path. A dev can register a buffer-built document under a chosen symbolic name into the same `module_context` the importer will use.
  - What's missing: `import_load_child` never checks "does this import name already resolve to a document I already have?" before going to the filesystem. The fix is one added check — look up the raw quoted import string against already-registered documents first, falling back to file resolution only on a miss — reusing the exact reuse-instead-of-reload mechanism diamond imports already use post-load, just triggered pre-load by name instead of by content hash.
  - Design call to make deliberately when this is picked up: match on the **raw quoted import string**, checked before `import_resolve_dir`'s directory-relative logic runs — not the *resolved* path, which would force the dev to predict the resolver's exact output (fragile).
  - Natural building block for the eventual class-based document-builder API (not yet designed) — a class wrapping "build a document, attach it as an import under a name" would be a thin layer over this.

- **`Time.now_utc` — wall-clock/calendar timestamp support in `sigma/time.h`/`time.c`**: `Time.now()` is deliberately `CLOCK_MONOTONIC`-backed (no epoch, duration-only — see its own doc comment). `Time.now_utc()` would be a separate, `CLOCK_REALTIME`-backed function for wall-clock/calendar use (logging, display), explicitly not to be conflated with `now()`/`elapsed()`. Likely paired with a calendar-breakdown helper (`struct tm` via `gmtime_r`, plus the `timespec` nanosecond remainder for sub-second precision, since `struct tm.tm_sec` is whole-seconds only). Not needed yet — no current caller.

- **SIMD-accelerated scanning — stretch-goal wishlist item, not a near-term target.** Raised during a throughput/benchmarking discussion: the technique behind parsers like simdjson (vectorized structural-character scanning — compare 16/32/64 bytes against delimiter characters in one CPU instruction instead of one byte at a time) could eventually apply to AML/AMP's scanner. The compelling use case is a web service parsing a high volume of ANVL documents/messages (AMP especially) per second, where sustained throughput matters far more than for one-off config-file parsing.
  - **Sequencing**: explicitly comes after, not before, the current iteration's arena-backed memory work and a working, benchmarked scalar parser. Optimizing a vectorized scanner before there's a correct scalar baseline to compare against and profile would be solving the wrong problem first.
  - **Target ISA**: AVX2 (256-bit, 32 bytes/instruction) is the realistic baseline to target, not AVX-512 — confirmed via `/proc/cpuinfo` that the dev machine (Intel Core Ultra 5 225F, Arrow Lake) has SSE2–SSE4.2/AVX/AVX2 but no AVX-512, consistent with Intel having dropped AVX-512 from consumer parts since Alder Lake. AVX2 is also the tier most SIMD-accelerated parsers treat as their primary path for the same reason (AVX-512 adoption is spotty/server-only).
  - **CPU, not GPU.** This is a host-CPU vector-instruction technique (AVX2/NEON), unrelated to GPU compute — parsing is branchy and latency-sensitive, and the data-transfer cost to/from a GPU would dominate for a workload this small and irregular. Not a fit for the discrete Arc GPUs on the dev machine.
  - **Real cost**: hand-written compiler intrinsics, per-ISA code paths, runtime CPU feature detection, and careful handling of tail bytes that don't fill a full vector width. Genuinely substantial, specialized engineering — not something to reach for casually.

- **`mmap`-backed source loading, threshold-gated — a new Sigma memory/`Allocator` feature, motivated specifically by Anvil.** Today's file-loading path double-copies: `Files.load` (`src/core/files.c`) reads the whole file via `fopen`/`fseek`/`fread` into a heap buffer, then `source_from_buffer` copies *that* into `anvl_source`'s own buffer before the intermediate is freed. The idea: for large files, `mmap()` the file descriptor directly and let the OS page cache back the source buffer, skipping both the `read()` and the copy entirely; for small files, the syscall/page-fault overhead of a real `mmap()` isn't worth it, so those would instead come from a reusable fixed-size block allocated (once) via the `Allocator`, avoiding a fresh `malloc` per small file.
  - **Threshold, not a universal switch**: somewhere around 64–128 KB is the working boundary — below it, fixed-block allocation; at or above it, real `mmap`. Exact cutover unmeasured, a starting guess like the arena-sizing multiplier was.
  - **Lives in Sigma, not Anvil**: this is general-purpose file-backed memory strategy, belongs alongside the existing bump allocator in `sigma/memory.c`/`sigma/allocator.h` as a distinct allocation mode — not something wired directly into `files.c`. Anvil is the motivating and (so far) only caller, but the mechanism itself is Sigma's.
  - **Sequencing**: unscheduled — raised as a design idea during the arena-sizing work, not yet needed by anything currently blocking.

- **Predicate-driven iterator for Sigma collections — a leaner alternative to `Iterator`/`Collections.create_iterator` for query-shaped access.** Raised while showcasing the existing generic `Iterator` in `test_body_amp.c`'s `AMP06` (a plain ordered walk over a `farray` view of `doc->body`). The repo owner has a prior implementation of this idea, mechanically equivalent to .NET's `IEnumerator` — hand the iterator a base pointer, a stride, and a predicate function with the ability to break out early, rather than requiring a heap-allocated `collection` view *and* a heap-allocated `iterator` object up front (today's `Iterator`/`Collections` pair always pays both allocations, and has no filtering or early-exit of its own — a caller manually loops and manually `break`s, after already paying for both allocations regardless of how soon a match is found).
  - **The win is allocation-zero query access, not just fewer lines at the call site.** A predicate-scan taking the raw base pointer/stride/count directly could answer a one-off "find the first match" or "does any element satisfy this" query with a single function call and no `Allocator.alloc` at all — strictly better than the current `Iterator` for that shape of access.
  - **Complements, not replaces, a `Map`-backed index** (Sigma already has one — `Map.create_iterator` returns a `sparse_iterator`, walked via `SparseIterator.next`/`current_value`, for key iteration) for lookups against the *same* keyspace repeated many times — e.g. the eventual Resolution phase's `$identifier`/inheritance-base resolution (see `notes/resolution-phase.md`), already expected to lean on `Map` for that. Using `Map` there is about repeated-lookup performance (O(1) vs. even a zero-allocation O(n) scan), not a rule the predicate-iterator enforces — it's a general-purpose query primitive usable against any collection regardless of access pattern; nothing about it is scoped to "one-off" use only. Internally, Anvil's own code (parser, resolver, etc.) always reaches for whatever's objectively best for the job — `Map` where lookups repeat, no laxity there. The predicate-iterator's real audience is consumers of Anvil as a library: primitives, not policy — a caller who doesn't have a known key to hand a `Map` (or has some other arbitrary, unpredictable query shape) still has a real query tool available, and if a caller reaches for it over `Map` even where `Map` would perform better, that's their tradeoff to make, not something the tool itself needs to prevent or steer.
  - **Lives in Sigma, not Anvil** — general-purpose collection-access infrastructure, belongs alongside the existing `Iterator`/`Collections` API, not wired directly into Anvil's own code. Anvil (`anvl_statement`/`anvl_value`/`anvl_slice` and friends — "our special collections and objects," in the repo owner's words) is the motivating case, same relationship the `mmap`-loading idea above has to `sigma/memory.c`.
  - **Sequencing**: unscheduled — noted for when an actual query/lookup need against Anvil's own structures shows up (Resolution phase is the most likely first customer), not a near-term target.
