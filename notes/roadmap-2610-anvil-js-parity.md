# Roadmap: anvil.js at parity with ANVL Native

Owner direction (2026-10-30):
- start with the reader;
- it must meet the performance expectations;
- it keeps native's zero-copy approach and principles;
- it replaces `anvil.node`;
- then add AnvilSchema, AnvilType, the writer and the builder, still with no AnvilScript;
- there **must** be a plan that keeps `anvil.js` in parity with ANVL Native;
- it follows the same TDD principles.

**Why.** Every JS binding builds the parse result as one JSON string in C, then has `JSON.parse` rebuild
it. That crossing has been the source of most of our recent speed fights: the attribute pass,
`numericKind`, blob tags. Removing that crossing is the only way past them. The 2026-09 benchmark
(`notes/flywire-parse-scaling-benchmark.md`) already showed a pure-JS reader beating `anvil-node` from about
1,000 records up (`anvil-node` was about 1.8x more per byte at 10k). A pure-JS package also removes the
native-addon platform limit (Linux x64 only), the WASM loading step (`ready()`, the `.wasm` file, the
Emscripten glue bugs) and the C/JS bridge code.

**The cost.** Two implementations of the grammar. Everything below is built so that a second
implementation **cannot drift** without a red build.

---

## 1. Principles (non-negotiable)

1. **Native is the spec. JS never defines behaviour.** When native and JS disagree, native is right
   unless an owner decision changes native first. JS follows native through the conformance corpus
   (§3), never through reading the C code and guessing.
2. **Zero-copy, as native does it.** A single forward pass, no lexer and no token array (native has
   none). The tree holds `{ start, end }` spans into the source buffer, never copied substrings.
   Values are materialised lazily, on first access, exactly where native does its work: string escapes
   on `asString()`, numbers on `asNumber()`/`asBigInt()`. The resolver is a separate pass over a
   collected list. Allocation is the JS analogue of native's arena: no per-node object until a caller
   asks for one (see §4, R0).
3. **Byte-exact semantics.** Offsets, line and column, NUL handling, blob bytes and error positions
   must equal native's. The input representation is decided by measurement in R0, but whatever it is,
   reported positions must match native's on the conformance corpus. A blob's bytes must round-trip
   exactly, including non-UTF-8, which today's JS bindings can't do.
4. **Numbers.** JS `Number(text)` is correctly rounded, so it is bit-identical to native's strtod in
   round-to-nearest mode, the only mode JS has. Integers past 2^53 are exact `BigInt`s. `numericKind`
   is judged from the spelling, as native does.
5. **One public surface.** The JS API is `anvil-node`'s current API, unchanged (`parse`,
   `parseRawValue`, `lastError`, `AnvlNode` and every accessor, `Schema`, `TypeRegistry`, `AnvilWriter`,
   `AnvilBuilder`), plus what is pending there (`blobTag`, `isNull`). Consumers swap the package and
   change no code.
6. **Strict TDD**, as in `agents/STANDARDS.md` §3:
   - the full failing test set first;
   - a genuine buildable RED, with stubs;
   - test by test to GREEN;
   - never changing a test's input to get a green.

   The conformance corpus *is* the failing test set for each phase. A phase starts with its corpus
   slice RED.
7. **Performance is a gate, not a goal.** See §5.

## 2. Who

A new sub-agent role, **JS Engineer** (`anvl-js-engineer`, Sonnet). It owns the `anvil.js` repo
(`~/Projects/repos/anvil.js`, today `anvl-js` 0.6.2-alpha). It will be rebuilt rather than extended,
because it predates `include`, the types, the schema, the writer and the current number grammar.

The **Core Engineer** owns the native-side parity tooling (§3: the dump tool, the corpus and the
generator). The **Verification Engineer** gates every phase on conformance, fuzz parity and speed. The
**Principal Engineer** merges.

## 3. Keeping parity (the MUST)

Seven mechanisms. Each one closes a drift path the others can't.

| # | Mechanism | Closes |
|---|---|---|
| P1 | **Native dump tool.** `anvil-dump` (C, in `anvil`) prints a canonical, deterministic description of what native produced: every node's kind, exact source span, decoded value, `numericKind`, blob tag and bytes (hex), attributes (raw and decoded), statement order, include resolution, and every error's code, category, message, line and column. Later phases add schema validation results, type-registry introspection, and writer/builder output bytes. | "same behaviour" becomes a byte-comparable artefact |
| P2 | **Conformance corpus, owned by native.** `anvil/conformance/`: input files plus expected dumps **generated by native**. It is seeded from every existing native fixture (`test/fixtures`, 129 files) and every native unit-test input, and grown by every BR/FR. A native CI check regenerates the dumps: if native's output changes and the corpus wasn't updated in the same commit, the build is RED. So every grammar or semantics change is an explicit, reviewed corpus diff. | silent native changes |
| P3 | **anvil.js runs 100% of the corpus.** anvil.js pins `vendor/anvil` (as the bindings do) and runs the whole corpus at that pin. A skip is allowed only with a ticket and the owner's OK. | JS lagging native |
| P4 | **Differential fuzzing.** A grammar-aware generator, plus a mutator over the corpus, produces valid and invalid documents. Native's dump and JS's dump must match on every one. Millions of cases per gate, and nightly on the Linode CI once it exists. Any mismatch is minimised and added to the corpus. | cases nobody thought to write |
| P5 | **Drift tests from the headers.** Error codes, categories, schema violation codes, format names, reserved words and keywords are read from `include/*.h` at the pin and compared with JS's tables. These are the same drift gates anvil.py and anvil.net already have. | enum and keyword drift |
| P6 | **Lockstep versions and releases.** anvil.js's version equals native's (`0.12.0-rc` with `0.12.0-rc`). Release tooling refuses to cut a release unless anvil.js passes 100% of the corpus at the release tag. There's one set of release notes. | shipping out of step |
| P7 | **Paired tickets.** Every native BR or FR that changes grammar, schema, types, writer or builder output gets a paired anvil.js ticket, filed by Triage and linked `depends_on`. The native ticket can't close until the corpus diff lands, and the JS ticket closes when JS passes it. The Verification Engineer checks both sides. | process drift |

## 4. Phases

Each phase follows the TDD order: the corpus slice RED, stubs, then GREEN test by test. Each ends at the
Verification gate (§5) before the next phase starts.

### Phase 0: parity tooling (Core Engineer, native)
- `anvil-dump` (P1) for the reader: nodes, values, attributes, includes and errors.
- `conformance/` (P2), seeded from the native fixtures and unit-test inputs. A `make check-conformance`
  target regenerates and diffs the dumps.
- The fuzz generator and mutator, with a harness that runs native and a second executable on the same
  inputs (P4).
- Header-extracted tables for the drift tests (P5).
- Done when the corpus is green against native itself, and a deliberately altered native build turns it
  RED.

### R0: representation spike (JS Engineer). Measure, don't guess.
- Build two or three thin prototypes of the scanner and value storage, covering headers, scalars,
  numbers, strings and objects:
  - (a) indexing the JS string directly;
  - (b) a UTF-8 `Uint8Array`, with lazy `TextDecoder` on slices;
  - (c) struct-of-arrays node storage in typed arrays, against plain objects.
- Run each on the §5 workloads against `anvil-node` and against v0.10.0-rc. Also check that each can
  report native-identical positions and byte-exact blobs.
- **Output:** a recommendation to the owner, with numbers. That decides the representation before any
  real code.

### R1: the reader (JS Engineer)
In corpus order: header and dialects (`#!aml`, `#!amp`; `#!asl` rejected as native does with ASL off);
comments; scalars (null, bool, bare, strings and escapes, numbers under the current grammar, blobs with
tags); arrays, tuples and objects (including the empty and one-element rules); attributes (raw and
decoded); statements and repeated names; `include` (files, plus the base directory and resolver from
FR-2610-anvl-include-001 once native has them); the resolver (`$ref`, inheritance); and errors with
codes and positions.

**Done when:**
- the corpus passes 100%;
- a 10M-case fuzz run shows no differences;
- the drift tests are green;
- the §5 performance gate passes.

### R2: anvil-node API parity (JS Engineer)
- The `AnvlNode` facade over the R0 storage, plus `parse`, `parseRawValue` and `lastError`.
- `blobTag` and `isNull` too (pending in anvil-node, so build them once here).
- **Acceptance:** anvil.node's own test suite (about 236 reader tests) runs **unchanged** against anvil.js.
  Plus FlyWire's and Rivet's suites, read-only, from scratch copies.

### R3: replace anvil.node (Principal Engineer, Release Engineer)
- anvil.js ships under the same API. The package name is an owner decision (D1).
- The FlyWire and Rivet notices, with each one's test results against the new package attached.
- The native addon stays available for one release as a fallback, then retires.

### S1–S4: AnvilType, AnvilSchema, writer, builder (JS Engineer, with the Core Engineer extending `anvil-dump`)
For each one, first extend `anvil-dump` and the corpus with native-generated expected outputs:
type-registry introspection and diagnostics; validation results (codes, field paths, messages); writer and
builder output **bytes**. Then the same cycle as R1: RED, then GREEN.

**Acceptance:**
- anvil.node's schema, types, writer and builder tests run unchanged;
- fuzz parity on validation and on writer round-trips;
- the §5 gate on validate and write.

## 5. The Verification gate (every phase)

1. **Conformance:** 100% of the corpus at the pinned native commit, with no unapproved skips.
2. **Fuzz parity:** at least 10M generated and mutated cases, 0 differences.
3. **Drift tests:** green.
4. **Performance**, measured the way the release gate does: interleaved, CPU-pinned, median of 101,
   both arm orders.
   - **Workloads:** the existing `parse-bench` set (FlyWire message, plain, attributed, tagged and
     untagged blobs, floats 3000, floats 10k × 10), plus real FlyWire and King & Crucible samples, and
     10k-row documents.
   - **Replacing anvil.node** requires anvil.js to be no slower than `anvil-node` v0.10.0-rc on
     **every** workload (≤1.00x). The target is faster at every size, including the small documents
     where the addon won in 2026-09. Any workload over 1.00x blocks the replacement until the owner
     decides.
   - **After replacement,** anvil.js is gated against its own previous release at ≤1.02x, as
     everything else is.
   - **Memory:** report peak heap and retained size per workload. No regression against `anvil-node`
     without the owner's OK.
   - **Browser:** the same workloads in Chromium and Firefox, **only through the contained harness**
     (`anvil.wasm` `test-browser/`).
5. **TDD evidence:** the RED run is recorded before the implementation commits.

## 6. Owner decisions (2026-10-30)

- **D1, the package (revised 2026-10-30):** anvil.js publishes under **its own name, `anvil.js`**,
  matching the repo and the Rivet project. It is **not** published as `anvil-node`. It has the same API
  as anvil-node, so a consumer's move is a dependency rename plus a version bump. `anvil-node` (the native
  addon) and `anvil-wasm` are deprecated at v0.11.0-rc, and those tarballs stay downloadable. The source
  repo stays private on the Linode box (`linode:repos/anvl-js.git`). Tarball: `anvil.js-v<version>.tar.gz`
  on anvldata.com, pinned by sha256.
- **D2, anvil.wasm (revised 2026-10-30):** ship `v0.11.0-rc` (with the browser fix and bundle), then **freeze and retire** it. `v0.11.0-rc` stays published as the record that answers "why not WASM?". anvil.js covers the browser too: it's plain JavaScript and runs in a browser as is. King & Crucible's web work is paused, so nothing depends on anvil-wasm.
- **D3, the old `anvl-js` 0.6.2-alpha consumers:** there are none. Nothing to migrate or freeze.
- **D4, include I/O in the browser:** confirmed. With no filesystem, the resolver callback
  (FR-2610-anvl-include-001) is the only route.

## 6b. R0 result and decisions (2026-10-30)

R0 (FR-2610-anvl-node-006, branch `spike/R0-representation` `2a5ff68` in anvil.js) recommends **(b) with i32 storage**:
- **input:** UTF-8 bytes (`Uint8Array`), so offsets equal native's byte offsets and blobs are byte-exact;
- **tree:** one `Int32Array` per parse, 8 ints per node;
- **objects:** `AnvlNode` facades are created only on access.

Against anvil-node v0.10.0-rc, parse-only came in at 0.04-0.14x and parse plus a full read at 0.13-0.47x, on every workload and size, in both orders. Retained memory is 41-46%. The owner **approved** it as the R1 design.

Also decided:
- **Cold start:** the first parse in a fresh process is about 2.5-3x slower than the native addon, until the JIT warms up (it catches up by about the 10th parse). **Accepted.**
- **Non-allocating accessors:** **deferred**, and backlogged as an anvil.node FR.
- **New for R1:** benchmark against `JSON.parse` too, as a reference. The owner's bar for the web is that ANVL must not lose to JSON.

## 6c. The native add-on retires too (owner, 2026-10-30)

The current native-addon `anvil-node` (repo `anvil.node`) **freezes and retires alongside anvil-wasm**:
1. It stays the published `anvil-node` until anvil.js passes the R3 replacement gate. That means 100%
   of the corpus, fuzz parity, and no slower on any workload, measured with the full grammar.
2. At R3, `anvil-node` becomes anvil.js. The last native-addon release stays published as the record
   that answers "why not a native addon?".
3. After that the `anvil.node` repo is frozen, with fixes only for anything that breaks users before R3.
   It is revived as a separately named package (for example `anvil-native`) only if one of these
   appears: (a) running AnvilScript's C VM from Node, or (b) a real short-lived-process use case where
   the native addon's cold start matters.

JavaScript users get one package, held to native by the corpus. Native stays the spec, and serves
Python, .NET and Java through their bindings.

## 6d. Consumer priorities (2026-10-30)

King & Crucible's browser requirements, from its Principal Engineer at David's request:
- **MUST:** loads without a bundler (a script tag global, or a vendorable ES module); the AMP reader
  (statement by name, `asString`/`asInt`, blob text, re-parsing a blob's inner text, `at`/`count`/`type`);
  the **AMP writer** (`statement().blob(tag,text).value(int).finish()`, byte-identical to anvil-py
  0.11.0-rc); exact native parity on escapes, blobs, tuples and integers; errors with line and column,
  never a thrown TypeError.
- **SHOULD:** `blobTag`; integers past 2^53 read exactly; AML reading; under 1 ms for parse plus read of a
  <10 KB message on a mid-range Android, precache-sized, measured against `JSON.parse`.
- **LATER:** schema in the browser, the builder.

FlyWire switches after S1-S4, since it uses Schema and AnvilBuilder.

**Resulting order** (Principal Engineer): R1 (reader) → R2 (API parity: browser ESM and global builds, plus
`blobTag` and `isNull`) → **S3 writer first** (K&C's MUST) → S1 types → S2 schema → S4 builder.

## 7. Risks

- **The R0 speed target isn't met.** If no representation beats `anvil-node` everywhere, we stop at R0
  with numbers, and the owner decides. Nothing is lost but the spike.
- **Corpus blind spots.** That's what the fuzzing (P4) and paired tickets (P7) are for. Every escaped
  difference becomes a corpus case.
- **Double the work per grammar change.** That's accepted by design. P2 and P7 make it visible and
  mandatory, never silent.
